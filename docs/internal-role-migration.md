# Internal role migration

The server-issued `internalRole` claim controls internal access. Old `leadOperationsRole` values map as follows: `management` to `admin`, and `sales` or `portfolio_owner` to `management`. Partners are excluded. Existing profile roles alone do not grant access.

Before rollout, back up Auth users and Firestore profiles/directories. Review the rules and application together in an isolated test project. Coordinate deployment and migration: new claims take precedence over legacy claims; users should refresh sessions after migration. This script is never run automatically by deployment.

Use an authorized, short-lived Google OAuth access token with Identity Toolkit and Firestore administration access in `GOOGLE_OAUTH_ACCESS_TOKEN`. The project and Firestore database are both required. The Firebase Auth claims are project-wide, even when the chosen Firestore database is isolated. Verify that the project and database match the intended environment before any apply. For an isolated staging project using its default database, run `node scripts/migrate-internal-roles.mjs --project=STAGING_PROJECT_ID --database='(default)'` for a dry run. Production uses database `ai-studio-7b4966a7-1d3f-4ab2-bcc5-924d7c1e1515`: the corresponding dry run is `node scripts/migrate-internal-roles.mjs --project=PRODUCTION_PROJECT_ID --database=ai-studio-7b4966a7-1d3f-4ab2-bcc5-924d7c1e1515`. Replace the project placeholders only after verifying them. These examples do not apply changes. Review every planned and skipped UID. For an internal account without a legacy claim, a trusted operator may create a private, reviewed JSON file mapping exact Firebase UIDs to `admin` or `management`, and add `--manifest=/path/to/file.json`. Do not commit that file. Unknown UIDs, conflicting claims, deleted profiles, disabled users and partner profiles are not migrated. Review and resolve all skips before rollout.

After reviewing the exact project and dry-run output, repeat with `--apply`. Each user's profile and both owner directories are committed together, then the custom claim is updated preserving other claims. If a claim update fails the script stops, and that user's profile/directory changes may already exist; inspect before rerunning. Reruns skip conflicts. The tool does not remove legacy claims or stale directory entries; assignment rules also require an approved internal profile. Refresh sessions after applying. No rollback is automatic: restore from the reviewed backup with a trusted operator if required.

Claims are not changed by editing a user profile. Future role grants, revocations and directory maintenance require trusted server-side administration. The existing partner workspace displays its own agreement/commission information from the partner record. Financial collection access is now admin-only. If partners require payout or payment records, provide separately scoped records and queries backed by trusted partner identity; the old unrestricted collection access is not a safe isolation mechanism.
